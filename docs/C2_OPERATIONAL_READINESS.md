## Actual `jobs.collect` token proof — unapplied workflow proposal

`docs/proposals/84-collector-token-proof.patch` changes **no active file**. Unlike #77's isolated `identity-only` push job, it prepares an auth-only step inside the real collector workflow, path `.github/workflows/reward-snapshots.yml`, ID `382300817`, job `collect`. The independent [#68 Actions-read patch](proposals/68-collector-actions-read.patch) remains separate and unapplied; both compose in a disposable-tree test.

The proof patch **preserves the current Contents-write permission map** for an initial approved baseline. GitHub's [permission rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions) set unspecified permissions to none when a map is supplied. The [workflow GET](https://docs.github.com/en/rest/actions/workflows#get-a-workflow), [run GET](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run) and [attempt jobs GET](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) document Actions-read for fine-grained access. Public-resource reads can have anonymous/public accessibility; we do not infer effective token access solely from the YAML or an owner-PC `gh` read. The proof always sends the actual `${{ github.token }}` and validates responses. A 403 can have several causes; it does not alone prove a missing grant.

If the baseline fails, **no anonymous, PAT, App-token or permission fallback** exists. Owner must diagnose the sanitized failure with private run metadata, and separately approve #68's exact `actions:read` addition if appropriate. After a reviewed permission-only change, approve a new exact main SHA/window and repeat only the read-only proof under that map. Success applies to the recorded workflow SHA and actual operations, not the old map, all future runs, Git CAS or provider collection. Explicit Actions-read is the recommended permission contract for a later guarded pilot; it is not applied here.

The prepared `scheduler/c2/collector_identity.py`:

1. Before token access requires exact repo/IDs, main workflow/job, scheduled event, GitHub-hosted Linux, owner `58099771` / `fuzzysniper`, first attempt, workflow SHA = run SHA = separately approved SHA, no external inputs, **absent gate attestation**, empty gate context and actor guard `342326617`. It rejects extra credential environment names without reading their values. The GitHub App cannot authorize this proof, even with blank inputs.
2. Requires exact `auth-only` arm and UTC window of at most 24h. Both now and actual run creation must be inside; creation age ≤120s. Queueing, stale approval or API propagation may safely fail. No timeout/window relaxation or automatic rerun.
3. Reuses `scripts.collection_gate.authenticate_run` and its authenticated transport for the same two identity GETs as the real gate. A third fixed GET verifies exactly one job, `collect`, running at the proof step with matching run/head. Pagination, other jobs, wrong current step, stale/completed/rerun/wrong actor/repository/workflow all fail closed. Socket timeout 8s, ≤128KiB/body, 25s total process deadline, no redirects/retries or arbitrary paths.
4. Prints one fixed-schema JSON receipt with fixed reason codes separating context/window, run/job validation and authenticated transport denial/unavailability. No exception/body/header is printed. Only a genuine approved execution can set `collectorWorkflowTokenVerified:true`; `hostedBindingVerified`, `gitClaimVerified` and `pilotReady` stay false, all dispatch/claim/provider/write counters zero. The empty gate context is **not an API attestation of variable absence**; that comes from the separate owner inspection.

Any **nonempty** `SCOUT_C2_COLLECTOR_PROOF` value freezes gate, collection, persistence and old-data/artifact publication in the patched workflow, even `false`, invalid case, expired window, failure or stray `collect=true` output. Only absence/empty restores original conditions. Proof checkout pins the run SHA and does not persist Git credentials. The job still receives its existing Contents-write-capable token; read-only behavior is enforced by reviewed proof code, not reduced job IAM. The patch does not alter triggers, concurrency, timeout or the default collection path when proof control is absent. Old-revision queued/in-flight runs do not inherit this protection; reconcile them **before** any future proof window. There is no durable global one-use ledger for these metadata GETs: multiple native runs can read within the approved window, but cannot collect. Unarming/restoring collection is an independent owner action, never a timed fallback.
