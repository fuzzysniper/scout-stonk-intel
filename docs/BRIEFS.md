# SCOUT Research Briefs V1

Issue [#12](https://github.com/fuzzysniper/scout-stonk-intel/issues/12). Daily briefs at `/brief/YYYY-MM-DD` summarize only supported recorded reward-counter changes for the reviewed token allowlist. `/brief` redirects to today's UTC date. `/api/brief?date=YYYY-MM-DD` exposes the same deterministic server-side report. There is no LLM, publishing job, new provider crawl, subscription, payment, wallet connection or trading feature.

## Daily scope and evidence gates

The date scopes a **UTC calendar-day target**, 00:00 inclusive to next midnight exclusive. Today remains in progress: daily totals and findings are withheld until the UTC day closes. Counts and actual in-day observation times remain visible; an incomplete day is never annualized or presented as a completed 24h result.

For each token, select the nearest actual recorded point at or before each requested boundary using the existing history interval selector. A counter at midnight may be the endpoint while in-day point counts exclude that next-day instant. The start baseline may be just before this day; comparison counts therefore differ from in-day counts. No missing boundary is interpolated. To publish a distribution change:

- Both boundaries must have actual points at/before them, at least two comparable points, and each endpoint must be within two hours of its requested UTC boundary.
- Actual span must be **24h through 24h + 60 seconds**, following Signal Lab's conservative duration policy. Shorter or materially extended intervals fail even if two endpoints exist. A stable minute-17 hourly cadence commonly selects two approximately 23:17 endpoints one day apart. This is an approximate UTC-day target with the actual interval and signed offsets disclosed, not a reconstructed exact midnight total.
- Every interior gap must be **strictly less than two hours**. Exactly two hours fails. Sparse history and missing hourly records do not become zero payouts.
- Every compared point needs finite nonnegative distribution counters, the exact verified quote mint and symbol, expected official source, and no conflicting duplicate. Distribution or detectable payout counter decrease anywhere in the segment is a reset barrier; no clamp, bridging, favorable older interval search or aggregation across resets is allowed.
- Malformed/future observation timestamps create the shared normalizer's global ordering barrier. Identical duplicates collapse, with warnings. Explicit non-reward mode is invalid. Optional provider generation must be calendar-valid, at most one minute ahead of its observation and at most three hours behind that observation. Missing optional generation metadata cannot prove independently fresh upstream data.
- Source must be available/cached. Degraded retained data and unavailable source withhold findings. Retrieved-at time never makes a missing observation fresh.

The result is the endpoint cumulative distribution counter difference, in that token's **verified quote units**. The API exposes actual endpoints, both raw counters when gates pass, observed seconds, point count, maximum gap, boundary offsets, quality reasons and provenance. UI explicitly calls this an increase in the recorded distribution counter. It is an API report, not independently reconciled transfers, per-holder yield, profit or a future reward promise.

API-reported payout-counter changes appear only when **every** compared point has a valid nonnegative safe-integer payout count without decrease. Missing counts produce null with a reason; they do not invalidate an otherwise supported distribution comparison or become zero. No holder-count claim is made. Quote mints distinguish STONK, USDC, ZEC, DKNG, NEAR and NVDAX; no raw cross-quote sum, dollar conversion or amount ranking exists. Even same-quote token distributions remain separate.

“Verified” means the recorded comparison passes these gates, not that the ecosystem or transactions are independently verified. Findings count supported **positive** distribution-counter changes; covered zero remains a supported “no increase.” When no positive findings pass, the headline is **No verified change to report**, with an explicit warning that missing data is not evidence of zero payouts. There is no invented materiality threshold or market-momentum claim.

## Historical freshness versus current collection health

For an archived day's factual comparison, endpoint freshness is evaluated against **that day's requested end**, not today's wall clock: an endpoint over two hours behind is missing coverage, and over three hours behind is explicitly stale. Provider generation is evaluated against its own observation. Otherwise every valid historical daily brief would expire merely because the day ended. This does not label old observations as current. Actual requested/observed times remain visible. Open days are labeled in progress; a future end boundary is never called stale before its deadline.

The **Data Quality** section is separately labeled a **current operational check**. It reuses Data Health, showing per-token latest actual record/age, current/delayed/stale/missing/quality/source state, expected missing slots, dated partial/failed/skipped outcomes, audit origin/time and diagnostic source retrieval status. It links `/status`, `/api/status` and Radar. Historical daily findings do not assert historical job health from today's summaries. Current health remains fresh through 75 minutes, delayed through three hours, stale above three hours; missed slots use minute-17 plus 15-minute grace, capped at 168, and estimate absent records rather than confirmed failed executions. Audit/attempt dates and overdue states remain independent of snapshot retrieval. Missing summaries never establish all-token success. See [DATA_HEALTH.md](DATA_HEALTH.md).

## Provisional editions, canonical URLs and sharing

Every date has one canonical path and date-specific metadata/Open Graph card. All editions, **including closed days**, are labeled **provisional reads of an evolving dataset**. Retention, corrections, newer observations, configuration and calculation policies can change a reread; no immutable daily archive is promised. The existing collector retains up to 193 points per token, by count, so older days can cease to have coverage. A valid older date still returns explicit missing/insufficient evidence.

The exact source-byte `dataset.revision` is displayed separately from a deterministic SHA-256 **brief version**. The brief version includes methodology identifier `utc-day-v1`, date, day-open/closed state, exact dataset revision, reviewed allowlist sorted by mint, and published per-token comparison fields/gates. It excludes retrieval/evaluation time and current collector warnings. Closing the day, a future record becoming usable, a source-safety gate changing, input bytes or allowlist changing creates a different version. Equivalent cached/available reads with unchanged claims preserve it. This is content attribution, not a signature or chain transaction proof. Future calculation-policy edits must bump the methodology identifier.

Copy link and Web Share use `/brief/YYYY-MM-DD?v=<64-hex-brief-version>`. Versioned JSON evidence similarly uses `/api/brief?date=...&v=...`. When the requested version differs, the API returns **409 `revision_changed` without replacement rows/amounts**; the page shows a revision warning and requires the reader to explicitly open the current provisional edition. It never silently redirects to new claims. If the source is cold-unavailable, 503 discloses unknown evidence instead. Historical versions are not fetched or persisted; save JSON for reproducible archival review. Versioned links can expire as data evolves, which is an intentional V1 limitation. The unversioned canonical URL remains useful for the current date-scoped edition.

The short mobile share card includes date, provisional label, honest headline and coverage counts. Native sharing runs only after a user click; unsupported sharing falls back to copy. Clipboard denial offers a selectable versioned link; user cancellation is quiet. No automatic posting, analytics, tracking, notification or third-party sharing endpoint is added. Date-specific Open Graph images contain generic evidence/coverage language, never financial amounts or stale finding counts. Live history/status/source links can evolve and are labeled live; the versioned brief JSON anchors each token's comparison evidence. Official identity links retain the existing dated capture provenance.

## Security, performance and cost

The API validates unique supported date/version parameters before source access. Dates must be real ISO calendar dates from 2020 through today UTC; versions are exactly 64 lowercase hex characters. Repeated, malformed, future or unsupported parameters return sanitized 400; invalid date pages return 404. User input cannot select an upstream URL, file, branch or arbitrary mint. Responses are `Cache-Control: no-store`; errors do not expose upstream messages, headers, paths or credentials. React escapes public names and evidence URLs derive solely from the existing validated allowlist.

Only the existing fixed GitHub history/audit/attempt sources are read, in parallel through shared bounded readers. History is capped at 2 MiB, diagnostics at 64 KiB each, with five-minute per-instance caching, eight-second deadlines, one-minute failure backoff and at-most-15-minute degraded retention. There is no deployment-local observation fallback. No new dependencies, credentials, database, infrastructure, collector changes, external AI API billing or workflow permissions are required. Existing hosting/Actions/GitHub egress limits and cold-start multiplication still apply. Calculations are bounded by the retrieved dataset and maximum ten reviewed tokens. Native share support requires browser capabilities; clipboard generally requires a secure context.

Trust remains the official API observations and reviewed GitHub main files over TLS. Counter precision uses JavaScript numbers; UI displays up to twelve significant digits and raw JSON is the numeric evidence. Gaps, provider caching, missing counts, legacy quote identities, short retention and strict one-minute matching tolerance can withhold comparisons. Complete coverage is not universal StonkFun ecosystem coverage. The seven tokens are the reviewed selection, not a ranking.
