## Implemented guardrails and precise limitations

- Native Render adapter now hard-pins **only** `srv-dbe1vc8m7kps73c2jju0`, `background_worker`, exact `https://github.com/fuzzysniper/scout-stonk-intel`. It verifies GET identity/hash before **one** suspend POST, then one GET acknowledgment. Another SCOUT worker is refused before I/O. Missing/changed identity,403/429/503, redirect, timeout or lost ACK is unconfirmed; no automatic retry. Each adapter also latches after its first attempt. `suspended` is control-plane evidence, **never native socket-closure proof**. There is no resume/deploy/billing/list operation.
- Telegram native adapter remains fixed-host,≤5s/32KiB, one POST, no retry/redirect, matching recipient/message ID/provider date/hash and bounded non-regressing local receipt clock. `provider_accepted` and `deviceDeliveryProven:false` are deliberate: an API response cannot prove an iPhone push/read. Original provider/local clocks remain separate. No source payloads or financial figures are sent.
- Emergency notification and Render suspension each reserve their own durable effect **before** network I/O, then run concurrently. A slow/unavailable Render API must not prevent the alert from starting. SQL STOP is attempted first if possible; absence of an ACK never becomes confirmed STOP.
- Actual cadence is **start-to-start10s**, not cycle duration+10s. Routine cycle budget8s; late wake-up>250ms, clock regression or an ignored/wedged dependency stands down without catch-up bursts or false `checked`. Aborted/late continuations cannot issue another port/effect operation. The kernel's30s assurance and existing source lease remain unchanged. This is a scheduling requirement, not a promise of10s mobile delivery under outages; measure actual start/receipt/suspension clocks.
- Runtime now requires an explicitly initialized, private POSIX journal identity, external recovery floor and exclusive writer lock. It does **not** create missing runtime history. File+directory fsync precede effect permission. Bad/malformed/rolled-back anchors, fsync/write failure or uncertain writer/driver closure fail closed and retain uncertainty; no PID-based lock reclamation. Existing simple `openJournal` stays available for historical disposable fixtures, never as the runner's fallback.
- Same-journal restart cannot resend an uncertain effect. This is **not global exactly-once across two independent disks**: each monitor has its own reservation. A complete privileged restore of journal **and** external recovery evidence cannot be detected locally. No automatic boot/restart/reinitialize/repair is approved. Before restart the owner must compare against the independently retained latest floor/receipts. For continuous GO, explicitly review per-actor idempotent STOP escalation, or separately review shared cross-host coordination if one total POST globally is required. No distributed store was fabricated here.
- A primary and separately approved secondary host are mandatory. Same host/failure domain, source Render worker, Vercel runtime/minute cron, missing durable disk or missing placement approval is refused before credentials. Names/acceptance hashes are **owner attestations**, not proof of physical placement. Verify both actual hosts independently.
- Both modes require a fresh≤20s signed liveness receipt from the other pinned peer, exact parent/grant/mode/epoch/key and monotonic sequence. Signature proves approved-key possession, not placement, device delivery, healthy billing or source GO. Reading a file never updates its clock. Missing peer blocks startup before credentials; loss after startup enters STOP handling. Health mode never renews the primary assurance.
