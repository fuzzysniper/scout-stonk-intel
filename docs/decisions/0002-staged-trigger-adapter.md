## Implementation and security decisions

Use the scheduled-only [Worker](../../scheduler/worker.ts) and one named SQLite Durable Object. No Worker public `fetch`, route, deployment manifest, Cron registration or real secret is supplied. `ACTIVATION` defaults off and must equal `human-approved` to act; setting that value is a future approved operation, not an authorization mechanism by itself. The test-only HTTP facade/clock/storage injection in `tests/scheduler-harness.mjs` must **never** be deployed. Production time is the Durable Object clock. The Worker requires the exact hourly Cron string and singleton name.

Slot IDs match the Python reference: `fuzzysniper/scout-stonk-intel|reward-snapshots.yml|main|YYYY-MM-DDTHH:17:00Z`. The coordinator atomically claims a unique SQL row/nonce, caps receipts at 193 with at most 386 attempt records and prunes only after eight days. Invalid, future or >15m late slots cannot replay after eviction. A reserved lease is 60s; expiry is uncertain, never permission for another dispatch. Accepted 200/204 is terminal, even if run details are malformed. Timeout, network loss, redirect or ambiguous 5xx stays uncertain. Only explicit 429 with integer Retry-After 1–300s permits one durable-alarm retry in the original window (two attempts total). 403 is never guessed to be a rate rejection. Late alarms terminate expired retries; alarm redelivery uses the same atomic gate. Alarm/storage persistence failure stops safely; operator inspection is required. Auth/config/scope failure or known bad dispatch configuration pauses the durable circuit. Even pre-dispatch API read outages conservatively pause; human review is needed rather than silently claiming recovery. No automatic unpause/reset/key replacement exists.

App JWTs use RS256, 60s clock skew and five-minute expiry, with a nonextractable imported PKCS#8 key. All outbound URLs are fixed HTTPS `api.github.com`, verified by the runtime; manual redirect mode prevents following redirects (workerd does not support `redirect:error`). Requests have eight-second timeouts; JSON responses are limited to 32KiB. No token/JWT/key/header/raw response/error is logged or written to the ledger. Tokens are opaque, never parsed as JWTs or constrained to old fixed lengths. Each attempt retains separate claimed/updated times, terminal/retry state, safe enum reason and optional run ID; retrying does not overwrite the first attempt’s evidence. Receipt exports hash the current private nonce and derive the fixed run URL from the validated ID.

The adapter verifies the installation's App ID, owner, selected-repository mode, unsuspended state and Actions write/implicit Metadata read only. It requests a token with explicit SCOUT repository ID and Actions write; checks expiry/returned permissions and the token's one-repository scope via `/installation/repositories?per_page=2`. **That narrowed token does not prove the App installation itself includes only SCOUT.** A human must separately inspect the entire installation grant. The App key can mint other tokens within its actual installation, so installation scope is a critical independent control. Normal dispatch uses four GitHub calls (installation lookup, scoped token, repository check, fixed dispatch). No Contents/Secrets/Variables/Admin permission is requested. Actions write can dispatch/cancel other workflows and delete Actions evidence in the repository; it is not workflow-specific. A compromised administrator/runtime can steal the signing capability; runtime secret storage does not eliminate this risk.

The only secret binding is `APP_PRIVATE_KEY`; App, installation and repository IDs are configuration, not secrets. Store the key in Cloudflare's runtime secret facility through a trusted human workstation, never GitHub workflow inputs, client code, URLs, local committed files, chat or PR logs. GitHub's downloaded App keys may be PKCS#1: an approved operator must convert to PKCS#8 locally, keep both copies private and remove temporary copies securely. No real key or App is created here. Tests generate **ephemeral in-memory mock RSA material**, unrelated to any account.

Rotation: pause external activation, preserve receipts, create a replacement App key through the approved owner process, replace the runtime secret while off, validate scope in an approved isolated check, revoke the old key, then obtain explicit resume approval. Emergency revocation: pause/delete Cron (up to 15m propagation), suspend/uninstall the App and revoke keys; existing installation tokens may remain valid until expiry/revocation, up to one hour. Inspect Actions and Git commits for unexpected operations. Never assume deleting one key cancels already-issued tokens. Never install on STORK Post Office, treasury or another repository.

## Shared protection: Git compare-and-swap before provider access

External dispatch deduplication cannot guard today's native/manual workflow. [The inactive shared planner](../../scripts/shared_collection_gate.py) supplies a **single journal claim policy for all three sources**, exercised with real local Git conflicts. It creates only control metadata, never reward samples. The future journal is a versioned 193-claim/eight-day file, separate from the live dataset; none is added to `data/` in this PR.

Every native scheduled run, manual run and external run must take the same gate under existing noncancelling concurrency. Native/manual slots are attributed from **authenticated actual run creation time**, using the previous minute-17 boundary; this is an attribution policy, not evidence of GitHub's intended schedule. All sources must start within 15m of that slot. Late native jobs/queues are rejected rather than assigned fake history. External input must be canonical, on main, workflow_dispatch and from the approved App bot's **numeric actor ID**. Empty external input, a forged source, arbitrary target/ref, rerun attempt or corrupted journal fails closed. Manual runs have no bypass/force/backfill override. Provider outages or a crashed claim consume the slot; the next genuine slot is recovery.

Future wiring, requiring separate human review of schema/workflow/permissions:

1. Declare `collection_slot`/`trigger_source` inputs on the existing workflow. Obtain the actual run record from authenticated GitHub context/REST; bind repository/workflow/event/branch/actor/run ID/attempt/creation time to that run, never user-supplied metadata. Record App bot ID out of band. If REST run reads require Actions read on the current workflow token, that permission change needs explicit approval. The existing workflow is unchanged here.
2. Read the journal and protected control files from an exact main checkout. Require run head/base SHA and current fetched main agree; a stale checkout must stop before collection. Use `plan_claim`, validate full existing journal and stage **only** the candidate claim file. Shared concurrency alone is not the lock.
3. Commit the claim with its exact base parent and push `HEAD:main` without force/rebase/merge/retry. **Before any provider fetch**, verify the accepted remote claim commit/parent and exact journal bytes. `publication_authorized` checks bytes/parent; caller must also verify exact remote commit ID and branch. Failed/uncertain push forbids collection, even if the push might have succeeded. Preserve local artifacts for inspection. The committed claim remains consumed after crash/restart/provider failure. If main races, the competing push loses safely, as the offline two-clone test demonstrates.
4. Only the confirmed claim owner invokes the unchanged collector. Its actual observed/provider timestamps, strict allowlist/quote/counter/coverage checks and partial-failure policy remain authoritative. Publish existing snapshot/summary from the confirmed claim base with existing no-force conflict behavior; preserve candidate/summary artifacts on failure. No blind conflict retry, fabricated merge, missed-slot catch-up or archive enablement.
5. Export run/claim/collection/accepted data commit references separately. Do not equate claim commit, HTTP acceptance or a green job with a genuine data commit. Independent inspection must join exact snapshot hash and per-mint summary to the remote data commit.

This policy costs an extra control commit per claimed slot (even failed collection). It is conservative: ambiguity, late queueing, journal damage and human main changes can sacrifice a slot. Protect/review the journal path and prevent concurrent writers from erasing claims. It cannot defeat a malicious repository administrator or code change bypassing the gate. **No active workflow calls the gate yet: activation remains blocked until the complete wiring and native/manual/external collision tests are reviewed and proven in an approved isolated environment.** Do not turn on this adapter against today's workflow; its undeclared dispatch inputs would be rejected and native duplicates would be unguarded. Coordinate/disable native cron only in that separately approved change.

## CPU and maximum infrastructure budget

[Measured evidence](../evidence/scheduler-cpu-benchmark.json), 2026-10-13: Node 20.20.2, pinned Miniflare 3.20250718.3/workerd 1.20250718.0 (compatible with Node 20 CI), x64 AMD EPYC 9V74, mock RSA-2048. Linux process user+system CPU measured at 100Hz, **10ms granularity**. Supported local Miniflare executes real WebCrypto and Durable Object SQLite; all GitHub responses are synthetic. No live App/provider/account call occurs.

| Measurement | Aggregate workerd CPU | Approximate CPU/operation |
| --- | ---: | ---: |
| 200 warm PKCS#8 import + JWT signing operations | 340ms | 1.7ms |
| 100 fresh SQLite objects + scope checks + mock dispatch | 450ms | 4.5ms |
| 100 repeat-slot checks | 70ms | 0.7ms |
| 100 thin scheduled-handler + repeat-slot DO checks | 60ms | 0.6ms composite |
| Five first dispatches in separate runtimes | 10, 10, 10, 20, 10ms | Tick-quantized, not an invocation percentile |
| Workerd startup before first request | 20–30ms/sample | Process boot, not billed handler CPU |

First dispatch wall times 16.3–39.5ms; runtime readiness 47.3–5062.0ms reflects local runtime/proxy lifecycle. Node mock/harness CPU is recorded separately. A zero tick delta means below measurement resolution, **not zero CPU**. Workerd aggregate CPU includes internal facade/proxy/SQLite/crypto/HTTP overhead across isolates, not Cloudflare's billed invocation CPU. Warm averages are not p95/p99; fresh objects differ from one production singleton. Local cold boot, actual key size, production edge placement, account quotas and current hosted compatibility behavior remain unknown. This is approximate engineering evidence, **not a hosted Free-tier pass or reliability claim**. Reproduce using `bash scripts/benchmark-scheduler.sh` (Linux only; writes a chosen evidence file).

**Assess CPU at the correct boundary.** The Cron Worker validates timing and forwards to the singleton; PKCS#8 import/signing, token scope checks, SQL and dispatch run **inside the Durable Object**. The [DO-specific limits page](https://developers.cloudflare.com/durable-objects/platform/limits/) lists **30s default CPU/request, configurable up to 5m**, while the [Workers limits page](https://developers.cloudflare.com/workers/platform/limits/) lists **10ms per Free Cron invocation**. [Dated source hashes](../evidence/scheduler-runtime-source-review.json) record this distinction. Comparing the aggregate fresh-DO benchmark directly to the Cron 10ms limit would be incorrect. The local first-dispatch composite cannot isolate the thin Worker’s CPU. Hosted validation must meter both separately and confirm actual account limits.

Use Free as the **conditional candidate**, not an approved activation: 24 slots/day, 720–744/month is far below the documented 100k requests/day, five Cron triggers, 50 subrequests and SQLite row/storage quotas in ADR 0001. Normal four GitHub calls/event means 96/day; max two attempts means at most 192/day. Receipt replay does not authenticate/dispatch. SQL work is bounded by 193 slot rows and 386 attempt rows; no WebSockets or busy timer. Actual GB-s, row billing overhead, account sharing and durable storage remain unmeasured. The thin Worker must satisfy the Free **10ms Cron CPU limit**; DO cold import/signing and complete coordination must satisfy its separate documented CPU/storage/duration quotas. Small aggregate warm values make Free plausible, but they neither isolate Cron billed CPU nor prove hosted cold-start/account behavior. Hosted measurements on the selected account/key remain mandatory before approving Free.

| Plan | Likely incremental monthly infrastructure cost | Budget decision |

| Workers + SQLite DO Free | $0 if all actual account quotas/CPU limits fit | Best <=$5 candidate, gated on hosted measurement and owner approval |
| Workers Paid + included SQLite DO | **$5 minimum**, plus possible usage/storage overages and taxes | Baseline already consumes the target; NOT guaranteed hard $5 ceiling. Reject activation unless owner verifies inclusive price, account usage and enforceable spending controls |

No automatic upgrade, purchase, card entry or spend occurs. GitHub App has no additional license charge for this design; actual owner plan/taxes/other resources are unknown. Official pricing references/hashes remain in ADR 0001's dated source ledger. Cloudflare quotas and pricing must be rechecked by the owner at setup. If Free fails and total Paid cannot be kept <=$5/month, **stop and reconsider hosting**; do not spend beyond target. No production metrics are invented to make Free appear proven.

## Human setup/activation blockers and 48-hour proving

Human approval must cover the dependency addition (dev-only Miniflare/workerd native binaries), control journal schema, App security grants, full workflow wiring/permissions and account-specific cost. Separately approve account creation/use, installation/key generation, secure secret handling, runtime/DO provisioning and deployment; none occurs in this PR. Select a current supported hosted runtime date, verify fixed target/API compatibility, owner/MFA/budget/rollback responsibilities, Free CPU or affordable Paid limits, no public routes, activation off, SQLite namespace migration and eight-day durable retention/export. Test scope and gate wiring in an explicitly approved isolated setup before another approval enables one hourly pilot. Do not use a production dispatch as an engineering test. Keep archive publication off.

After that separate approval, record **48 consecutive canonical hourly slots**, not a selected set of successful jobs. Join planned slot, external delivery/claim/attempt/updated time, hash-redacted receipt, API accepted status/run ID (nullable legacy receipt), actual run actor/event/creation/start/finish, Git claim SHA/parent, per-mint real observation/provider times, summary candidate SHA-256, remote accepted data commit/parent and served hash after existing cache expiry. Store operator-held exports outside Cloudflare/GitHub so compromise/evidence deletion is visible. A claim hash is correlation, not a signature. Ambiguous acceptance requires bounded human read-only reconciliation against exact slot/actor/run; missing API/list results do not prove no dispatch. Never re-POST to resolve uncertainty.

Pass all ADR 0001 gates: >=47/48 jobs created within 15m; <=1 accepted external dispatch/slot and **zero unintended duplicate collections across all sources**; no unresolved acceptance/claim/data-persistence result; explicit failed/partial providers; maximum real observation gap <=2h and latest observation age <=3h; verify per-mint/source/quote identities and exact remote/served hashes. The stricter research calculation coverage gates remain unchanged, so a passing pilot does not manufacture 7d history or unlock unavailable comparisons. Report all 48 slots, denied/unknown/missing values and account CPU/GB-s/row/request/artifact charges. Stop/pause on duplicate, unexplained conflict, auth/scope drift, quota error, gap/freshness failure or budget risk. No public reliability claim before independent human review. Test duplicate/outage simulations only within approved isolated scope, never with invented production samples.

## Rollback and limitations

Preparatory rollback is a reviewed revert of this PR (including dev dependency/lockfile). There are no live resources, credentials, workflows or data changes to undo. Future pilot rollback: turn activation off first, remove external Cron through the approved owner process, allow up to 15m propagation, preserve uncertain receipts/operator evidence and all genuine observations/claim/data commits, revoke/suspend App installation and keys, then remove only explicitly approved resources. Existing tokens require separate expiry/revocation review. Never delete real data, force-push main, replay missed slots, enable archives, alter financial math or change treasury/tokenomics as recovery. The native schedule/permissions remain untouched until separately reviewed.

The local runtime is older than the dated API/pricing sources because CI pins Node 20; live compatibility is unproven. No external scheduler is provisioned/deployed, no secret is configured, no live workflow is enabled/dispatched, and no 48h pilot has run. A shared claim algorithm and races are tested, but full production workflow integration is deliberately absent. Exactly-once behavior across network/ledger/Git cannot be guaranteed; fail-closed decisions preserve authenticity at the cost of gaps. No UI changes: screenshots do not apply.
