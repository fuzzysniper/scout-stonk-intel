# Shared collection claims — inactive workflow integration

Issue [#28](https://github.com/fuzzysniper/scout-stonk-intel/issues/28), based on main `82731c69096ed250c4393b1de186a3f25653e07b`, including merged PR #27. Extends [ADR 0001](decisions/0001-collection-trigger.md) and [ADR 0002](decisions/0002-staged-trigger-adapter.md). **PR review only. No gate flag, credentials, permissions, external service or pilot is activated here.** Merging code and approving a migration are separate decisions.

## Default-off behavior and workflow wiring

The existing main-only `reward-snapshots.yml` declares optional `collection_slot` and `trigger_source` inputs for a future external dispatch of **the same workflow**. There is one collection entry and one shared journal for native, manual and external sources. The Cron string, five-minute timeout, shared noncancelling concurrency, workflow permission block (`contents: write` only), existing collector command, partial/all-failed handling, snapshot/summary publication block and seven-day artifact retention remain unchanged.

`SCOUT_COLLECTION_GATE_ENABLED` is a repository variable, default unset/off; `true` opts into the gate **only after separate human approval**. Ordinary native/manual runs with empty inputs skip the entire gate step while unset/false and execute the original collector/publisher directly. They do not depend on new API access, journal writes or gate receipt availability. The library's disabled path also performs no API/Git operation. External-style inputs, a configured App actor trying the plain entry, and invalid opt-in values invoke the gate to fail closed when disabled; they cannot fall through to legacy collection. GitHub expressions compare strings case-insensitively; the CLI accepts only lowercase `true`/`false`/empty, so use those exact settings (uppercase true stops closed).

| Entry | Integration off | Integration explicitly on |
| --- | --- | --- |
| Native schedule, empty inputs | Original collection behavior | Authenticate actual run, resolve attributed slot, claim/confirm before provider access |
| Ordinary manual dispatch, empty inputs | Original collection behavior | Authenticated User actor, same slot gate; no force/bypass/backfill |
| External inputs or configured App actor | Block before provider/publisher | Authenticated approved Bot actor + canonical slot + claim/confirmation required |
| Invalid setting or enabled gate failure | Block; no legacy fallback | Block; preserve receipt/candidate evidence |
| Existing consumed slot | Legacy behavior while off; no dedupe claim | Successful explicit skip; no provider query/data publication |

Source inputs are environment bindings, never interpolated into shell commands. Empty inputs remain valid for the old manual UX. This PR does not send a live dispatch or alter repository variables. **Variable visibility check returned GitHub HTTP 403 (`Resource not accessible by integration`) for both gate/App actor variables. Their live state is unknown. A human must confirm unset/false before merging; never assume code default proves current settings.** No permission escalation is requested/performed to inspect them.

## Authenticated identity and trust boundaries

[The adapter](../scripts/collection_gate.py) requires the fixed repository, `refs/heads/main`, exact workflow ref, `collect` job, event schedule/workflow_dispatch, valid numeric run/actor/repository IDs, first attempt and hexadecimal context SHA. Using the existing ephemeral Actions token, two bounded authenticated GETs retrieve the fixed workflow and actual run ID. API responses must agree on repository ID/name, workflow ID/path, main branch, head SHA, event, actor/triggering actor, first attempt and running state with no conclusion. Old completed/cancelled runs, reruns, fork/branch/workflow mismatches and forged input IDs cannot authorize collection.

The API path supplies workflow identity, not arbitrary user URLs. HTTPS/TLS remains enabled; redirects are rejected before following, responses limited to 128KiB, socket timeouts eight seconds, no API retries, and the Linux gate process has a 60-second deadline including Git and receipt output. A token may need separately reviewed Actions read access depending on actual GitHub policy/resource visibility. **This PR does not add `actions: read` or any live permission.** If current access is insufficient, an enabled gate fails closed on 403; the owner must obtain explicit approval for the narrow read permission before migration. No anonymous/PAT/App-key fallback exists.

External mode additionally requires `trigger_source=external`, the exact canonical slot, and `SCOUT_COLLECTION_APP_ACTOR_ID` matching authenticated numeric **Bot user ID**, not App ID, installation ID or a login supplied in inputs. The owner must verify that ID and SCOUT-only App installation out of band. A configured App cannot masquerade as manual/native, and other Bots cannot take the gated plain manual path. Native events are authenticated GitHub schedule creations; their actual creation time is attributed to the preceding UTC minute-17 boundary. This **does not prove GitHub's intended schedule**. Delayed jobs outside the original 15-minute window stop instead of backfilling; queue delay also counts. Clock regression/future slots stop.

Only GitHub workflow checkout credentials can publish the control claim; the external App retains Actions write only and never receives Contents write or the workflow token. The API client sends the ephemeral token solely to the fixed GitHub API origin. Git uses the checkout's existing credentials and a pinned GitHub origin, never user-supplied remotes in the CLI. Git stderr/API exception bodies/tokens are captured or discarded, never logged. No new real credential, key, secret store or account is configured. Tests inject synthetic identities/tokens and disposable local Git remotes.

## Exclusive Git CAS before collection

`data/collection-slots.json` is a **new empty, inactive control journal**, not a reward dataset. Version 1 matches the existing planner schema: canonical slot, native/manual/external source, run ID, claimed time and exact base SHA. At most 193 claims/eight days and 128KiB; no TTL release of crashed claims. The initial empty file requires human schema review. A missing, corrupt, symlinked, dirty or oversized journal fails closed; absence never initializes/erases history automatically.

1. Authenticate before publication. Require a clean tracked checkout, pinned origin and exact agreement between authenticated run SHA, local HEAD and fetched main. A queued stale head or audit/human commit before preparation stops; no implicit checkout/rebase/merge to a newer base.
2. Validate the entire journal and timing/source policy through the shared planner. A previously consumed slot returns an explicit duplicate skip even for a different run/source. Reruns remain rejected. Write only the bounded candidate journal atomically; stage only that file. Refuse unrelated staged/unstaged changes. No provider is queried here.
3. Create a single-parent claim commit on the exact base, fetch/check main again, then push immutable claim SHA to `refs/heads/main` with normal Git compare-and-swap (no force). Audit/collector/human races reject the stale update. The prepush check is not the lock; Git's remote ref update is.
4. **Require an advancing porcelain push result**, not only exit 0. Two identical invocations can create the exact same Git object; Git's `=`/up-to-date result must not authorize a second collector. Reject up-to-date, new-branch, forced, ambiguous or unexpected results, even when remote bytes happen to match. A losing publisher cannot collect. Lost responses, timeout or interruption after possible acceptance stay unknown and stop; no push retry or inference from a later read.
5. Following exclusive success, fetch main again and confirm exact claim SHA, single parent equal to the base, exact candidate journal bytes/hash, clean local HEAD and still-open 15-minute window. A successful push followed by main advancement/readback mismatch/read failure forbids collection. Persist the safe receipt and Actions output; only successful output emits `collect=true`. A receipt/output failure blocks the next step. The workflow's collector/publisher conditions require that authorization; default step success semantics block downstream work on gate failure.
6. Invoke the **unchanged** allowlisted collector only after confirmation. Real provider/observed timestamps, quote identity, counter/reset rules, genuine append-only observations and coverage gates remain authoritative. A slot is trigger metadata, never an observation timestamp. Partial collection persists only successful genuine records; all-failed collection still writes its actual failed summary and fails the job. Publish snapshot/summary from the claim commit with the unchanged non-force block. A later main conflict preserves candidate artifacts and fails; never re-collect/rebase/force-push to “repair” it.

One consumed claim remains consumed after crash, all/partial provider failure, uncertain acceptance, failed data publication or retry. A fresh next hour can recover using genuine new observations; the earlier gap stays missing. Full native/manual/external collision and identical-run tests exercise real local Git without relying on GitHub concurrency. The unchanged concurrency group still limits expected audit overlap, but queue order is not an hourly guarantee. Human pushes can race after confirmation; the data push safely fails while the durable claim still suppresses duplicate collection. Exactly-once collection/persistence across Git/network/provider cannot be guaranteed; this design intentionally sacrifices uncertain slots.

## Operator evidence, failure handling and costs

For enabled/blocked entries, the gate writes `${RUNNER_TEMP}/scout-collection-gate.json` and a job summary with safe decision, collect authorization, actual checked/run creation times, run/actor IDs, source/canonical slot when validated, base SHA, candidate SHA-256, local claim SHA, push stage and confirmed main SHA. These are fixed/sanitized fields; a receipt never contains API bodies/keys/headers. Claim/data commits and their parents are separate evidence. A separate `collection-gate-*` artifact retains the candidate journal and receipt for seven days. The original `collector-evidence-*` artifact keeps its existing snapshot/summary paths/layout unchanged, including while disabled. On skipped collection those latter files may be **previously committed files**: their original run/times remain authoritative, not the current artifact name. A green duplicate skip is not successful collection or recovery. Off-path gate receipts are absent by design; use existing collection evidence.

Decisions identify authentication/config/clock/journal errors, prepush main races, rejected/uncertain/nonexclusive push, failed confirmation, window expiry and explicit duplicate suppression. `attempted_unknown` is never treated as accepted. A consumed but unresolved slot requires independent read-only reconciliation of actual remote claim/run/data commits and file hashes; never clear it or repeat collection. Keep operator-held exports outside GitHub/Cloudflare because Actions write can delete Actions evidence. Claim hashes/receipts are correlations, not signatures or proof of data persistence. A compromised repository administrator/runner, disabled protection, force-push, malicious workflow revision or journal erasure can bypass the trust model; protect/review the control path and maintain independent records.

The gate adds no hosting fee. A pinned dev-only `@actions/expressions` 0.3.61 dependency interprets the real workflow conditions offline; the Python runtime uses only the standard library. That dependency requires explicit human PR review under AGENTS.md. Enabled mode adds two API GETs/claimed or duplicate entry, up to three bounded Git fetches plus one non-force push and one local control commit per successfully claimed slot (720–744/month). Missing/rejected claims can use less. Control file max 128KiB bounds one seven-day hourly artifact stream to 21MiB before compression; actual journal is much smaller and source snapshots/artifacts/account usage still dominate. Runner/API/clone overhead and account-wide artifact charges must be measured; no cost or reliability SLA is claimed. ADR 0002's conditional Cloudflare Free recommendation and maximum $5/month infrastructure target remain unchanged and **are not spending authorization**. Paid $5 baseline plus possible extras still requires total-budget approval. No external service is activated here.

**Main-push side effects require review before opt-in.** The current build workflow runs on every main push, so a claim-only commit adds another full CI run per slot (up to 720–744/month beyond existing data/audit commits). Existing Git-connected hosting may also build/deploy on each main commit; the owner must inspect its actual triggers, usage and billing. Do not assume a control commit is deployment-free. Before activation, separately approve any necessary CI/hosting path filters or automation policy so claim-only commits cannot cause unapproved production deployments or budget overruns. This PR changes neither that CI trigger nor hosting settings, and does not publish a real main claim.

## Exact human migration and stop/go gates

1. Review this PR's workflow/security/journal schema under AGENTS.md. **Before any merge**, the owner confirms gate variable unset/false and checks that no configured App actor can accidentally take the native legacy path. GitHub variable read access is blocked for this agent (403). Human review/merge must not silently activate the flag.
2. Separately approve an isolated proving setup for the complete wiring. Check real trusted Actions context, REST fields, repository/branch visibility, checkout token access, run-detail dispatch semantics, main-push CI/hosting side effects and the main-branch bot publication policy. If Actions read is necessary, submit/approve only that permission in a separate change; do not weaken branch rules or grant the external App Contents write. Confirm initialized journal and protected path. Local tests are not hosted validation.
3. Obtain **explicit approval to migrate native/manual collection to the shared gate**. Set exactly `SCOUT_COLLECTION_GATE_ENABLED=true` only in that approved scope. Confirm actual claim update, parent/hash and receipt before provider access; verify duplicate/manual/rerun/outage scenarios in the isolated scope, not through unapproved production dispatches. Gate on means failures stop closed; there is no runtime legacy fallback. Manual runs become minute-17/15-minute-window constrained, including intentional duplicates. Document/approve that behavior change before enabling.
4. Separately approve vendor/account use, SCOUT-only GitHub App installation/Actions write, Bot actor ID, secure key rotation/revocation procedure, hosted CPU/quotas and total cost. Configure the nonsecret `SCOUT_COLLECTION_APP_ACTOR_ID` only after verifying the authenticated Bot ID. The adapter stays undeployed/inactive until explicitly approved; never use real secrets in PR logs or tests.
5. After isolated proof and **another explicit pilot approval**, coordinate native Cron: disable/remove its schedule in a separately reviewed change once all sources are gated and claims work, or explicitly approve overlap under the shared guard. Do not leave unguarded native/manual collectors alongside an external pilot. Keep at most one external hourly trigger, activation off until approved, no public trigger route. No script in this PR toggles GitHub settings, schedules or Cloudflare resources. Do not activate external collection as a workaround for an unresolved gate failure.
6. Enumerate **48 consecutive UTC minute-17 slots**. Join external receipt/attempt, actual authenticated run/source/creation/start/finish, Git claim commit/parent, genuine per-mint observation/provider times, collection summary/candidate revision, accepted remote data commit and served hash after existing cache expiry. Require >=47/48 jobs within 15m, <=1 accepted external dispatch/slot, **zero unintended native/manual/external duplicate collections**, no unresolved claim/acceptance/data persistence, explicit provider failures, maximum genuine gaps <=2h and latest age <=3h. Strict research/7d coverage stays unchanged. Save independent operator evidence and actual account costs; report every rejected/missing/unknown slot rather than choosing successful jobs. Pause pilot on duplicate, auth/scope/quota/budget error, unexplained conflict, stale/gap violation or unmatched evidence. No 48-hour pilot has run here.

## Manual rollback

Before activation, a reviewed revert removes this inactive integration/journal schema; no real claim/data exists from this task. After a future pilot, first obtain/execute the approved external pause (allow Cloudflare Cron propagation up to 15m) and stop new dispatches. Preserve receipts, candidate files, all consumed claims, real observations, data commits and archives; suspend/revoke the App/keys and account for outstanding installation tokens as ADR 0002 describes. Review any in-flight unknown claim/data publication before changing modes.

Returning the gate flag to unset/false restores the old native/manual collector **without shared duplicate protection**. Do this only after external production dispatch is stopped and in-flight/queued sources are reconciled; remove/restore native Cron only in the approved rollback change. Never switch off the guard while an external producer remains active as an emergency “fix.” External-style inputs remain blocked while off. For code rollback, preserve a nonempty journal separately and retain Git history; do not blindly remove real claims/data or revert later bot commits. Never release consumed slots, fabricate missing samples, force-push, enable archive publication, trade, change tokenomics, access wallets/treasury or modify STORK Post Office as recovery.
