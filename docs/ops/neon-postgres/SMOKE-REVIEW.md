| Area | Finding and resulting behavior |

| Role escalation | Original checked only login flags. Also reject any transitive role membership outside self/runtime, ineffective runtime membership, elevated runtime-group flags, membership ADMIN and schema-USAGE/function-EXECUTE grant options. Require login + INHERIT. This is deliberately conservative; a legitimate extra membership also stops the probe for review. |

## What a genuine future PASS would prove

With the [approved runtime procedure](PRODUCTION-EXECUTION.md), it establishes one native pg connection from that independently identified Vercel production Node execution to the pinned, CA/hostname-verified Neon TLS peer, authenticated as current/session `scout_mint_app` in `neondb`. It records non-recovery status, observed time agreement, the enumerated effective permissions, read-only repeatable-read metadata transaction, acknowledged rollback and successful close. It does not establish future availability, public product readiness or permission to activate RPC. Function EXECUTE permission does not verify the deployed function body/schema hash, stored policy rows, bootstrap correctness or live quota/lease behavior; those remain separate activation-review gates.

Node's TLSSocket verifies the client-to-Neon peer. PostgreSQL's `pg_stat_ssl` is server-reported backend-session evidence; a proxy may terminate/reestablish TLS, so these are not proof of one end-to-end TLS session through every provider hop. Requiring both TLS observations is a conservative, **not yet hosted-verified compatibility gate**. If the provider does not expose the expected backend TLS row/protocol, stop and review that topology; do not silently remove certificate checks or report either “all transport proven” or “TLS broken” from this probe failure alone.

**SCRAM remains unobserved.** Pinned pg 8.23.1 `lib/crypto/sasl.js` prefers SCRAM-SHA-256-PLUS when offered with channel binding; it can fall back to SCRAM-SHA-256. `lib/client.js` also handles other authentication requests and clears its SASL session after authentication. `enableChannelBinding=true` is preference/support, not “require PLUS.” Neither TLS success nor `pg_stat_ssl` reveals the actual authentication mechanism at a Neon proxy/backend boundary. The report deliberately says `authenticationMechanism=not_observed`. Exact negotiated authentication would require separately reviewed client-protocol observation and/or provider-side evidence; do not inspect password verifiers, dump packets, monkey-patch auth callbacks or call TLS success “SCRAM-PLUS verified.” Local tests use a known SCRAM-configured server, not evidence about Neon negotiation.

**Privilege scope is explicit.** This is not an audit of every function, extension, other schema, database or future grant in the account. Database TEMP is not asserted denied; PostgreSQL READ ONLY alone permits some temporary/session effects. The *fixed metadata-only SQL inventory*, pinned catalog resolution and no step/network/provider imports are essential. No arbitrary SELECT or user-controlled function is executed. Acknowledged rollback ends this SELECT-only transaction; it does not simulate rollback of an attempted hosted write. Normal server authentication/query telemetry and compute consumption can occur. No “zero infrastructure side effects” claim is made.

Offline native tests additionally prove real read-only DML rejection on a **disposable local canary table**, effective grant failures, strict TLS and unchanged complete local policy/client/cache contents. Owner-only fixture setup changes only local synthetic state. No hosted write attempts or owner counter snapshots are needed for this smoke, and no owner credential is exported to obtain them. Continuous unrelated activity would make naive before/after production counter comparisons ambiguous anyway.
